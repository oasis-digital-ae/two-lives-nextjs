# Two Lives Theory — Next.js

A Next.js (App Router) port of the static Two Lives Theory site that keeps the
design pixel-for-pixel. It does that by **not** rebuilding the design: the
static site's compiled stylesheet and its jQuery/Swiper/anime.js stack are
shipped as-is, and only the page markup is turned into JSX. All 62 pages are
ported and checked against production with `tools/compare-pages.mjs`.

## How it works

| Static site | Here |
|---|---|
| `css/site.min.css` | `public/css/site.min.css`, linked as a plain render-blocking stylesheet from `components/ThemeLayout.tsx` (not imported through Next's CSS pipeline, so nothing gets rewritten) |
| `js/jquery.js` + `vendors.js` + `main.js` + `app.js` + inline scripts | `public/js/site.js`, one bundle built by `tools/build-theme-js.mjs`, loaded after hydration with `next/script` |
| page markup | `app/**/page.tsx` and `content/**/*.tsx`, generated by `tools/convert-html.mjs` |
| `<head>` tags | the `metadata` export in each generated page |
| `<body class="...">` per page | one root layout per route group: `(home)`, `(site)`, `(contact)`; the theme styles the header through those classes |
| journal / blog posts | `content/journal/<slug>.tsx`, `content/blog/<slug>.tsx`, rendered by `app/(site)/{journal,blog}/[slug]` (static params from the slug map) |
| `/.netlify/images?url=...` image URLs | unchanged. Netlify's Image CDN answers them in production; anywhere else a rewrite in `next.config.ts` serves the original file |
| GTM | the static site had it injected by Netlify; here it is in `ThemeLayout` |
| Supabase "Recent Posts" / listing grids | same browser scripts, loaded by `components/SupabaseScript.tsx` after supabase-js |
| netlify.toml redirects | `redirects()` in `next.config.ts` |

**Why the bundle replays events.** The theme registers dozens of
`DOMContentLoaded` and `window.load` handlers. In Next the bundle runs after
both have fired, so `tools/theme-shim.js` captures those registrations while
the bundle executes and fires them afterwards, in the order a browser would.
The same shim runs the pages' former inline `onclick` handlers (`data-onclick`).

**Why JSX is generated with an HTML5 parser (parse5).** React compares its
server HTML with the DOM the browser builds. Converting the source text naively
leaves differences (implicit tag closing, a leading BOM, `selected` on
`<option>`) that show up as hydration mismatches. Parsing the way a browser
does avoids that.

## The theme bundle, and what was cut

`vendors.js` on the static site carries 24 libraries; the pages use 12. The
bundle keeps Atropos, GSAP core (the carousel drag cursor tweens with it),
imagesLoaded, appear, countTo, the Crafto parallax, Retina, Skrollr and
Splitting from `vendors.js`, and rebuilds the three big ones from npm at the
same versions with only the used parts (`tools/vendor-lite/entry.js`):

- Swiper 11.2.10 with Navigation, Pagination, Autoplay, Keyboard, FreeMode
- Bootstrap 5.3.7 with Collapse, Dropdown, Tab
- anime.js 4.1.3 with `createTimeline` and `stagger`

Dropped entirely (no page uses them): Isotope + Masonry, Magnific Popup,
mCustomScrollbar, Justified Gallery, Particles, Carto portfolio, jQuery
Cookie, Final Countdown, Easy pie chart, FitVids, Smooth Scroll, Sticky-kit.
`main.js` guards every optional plugin with a `typeof` check, which is what
makes this safe.

Over the wire (brotli): 225 KB → 145 KB for the theme JavaScript.
`node tools/build-theme-js.mjs ../two-lives --full` rebuilds the unpruned
bundle if a page ever needs one of the dropped libraries.

## Checking a change against production

```bash
npm run build && npx next start -p 8889          # a production build, like Netlify serves
node tools/compare-pages.mjs --base http://localhost:8889 --sitemap
node tools/compare-pages.mjs --base http://localhost:8889 --paths /,/about --width 375
```

For every path it loads the local page and the live one in headless Chrome,
waits for fonts and lazy images, and compares each section's offset and height,
the page height, the number of initialised carousels and any uncaught errors
the live site does not also throw. Use a production build for this: `next dev`
recompiles per page and ran out of memory under the full run.

## Porting a changed or new page

```bash
node tools/port-pages.mjs ../two-lives          # everything, idempotent
# or one page:
node tools/convert-html.mjs ../two-lives/about.html "app/(site)/about/page.tsx" /tmp/report.json AboutPage
```

Read the report: inline scripts it skipped, `!important` inline styles,
`warnings`. Then `node tools/build-theme-js.mjs ../two-lives` if the theme
scripts changed.

## Develop

```bash
npm install
npm run dev      # http://localhost:3000
npm run build
```

Known and pre-existing: the theme's Swiper `slideChange` handler throws
`Cannot read properties of undefined (reading 'querySelectorAll')` once per
carousel on the static site too. Harmless, but noisy in the console.
